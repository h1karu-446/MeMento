# MeMento 性能改善・検証レポート

測定日: 2026-10-01 (JST)。アプリはローカル変更、DB migration 2件は接続先Supabaseに適用済み。アプリの本番デプロイは未実施。

## 実測比較

同じ端末、Node.js v24.15.0、Next.js 16.2.3の `next build` / `next start --port 3100`、同じSupabase・デモアカウントで比較。各画面1回ウォームアップ後、5回測定した中央値。Node fetch開始からHTML全体の受信完了までの時間で、ブラウザの描画時間・LCP・本番Vercelのレイテンシではない。前後の測定は順次実施のため外部ネットワーク変動を含む。

| 画面 | 変更前 | 変更後 | 短縮率 |
|---|---:|---:|---:|
| ダッシュボード | 397ms | 70ms | 82.4% |
| レビュー | 96ms | 60ms | 37.5% |
| ダイアリー | 104ms | 49ms | 52.9% |
| 英語学習 | 84ms | 53ms | 36.9% |
| ワード | 100ms | 52ms | 48.0% |
| マイページ | 581ms | 119ms | 79.5% |

デモアカウントのレビュー・日記・英語学習・ワードは0件。したがって一覧の実測改善は認証通信などの効果であり、大量データ転送削減の実測証明ではない。空一覧ではURL状態等の追加によりHTMLは約0.5KB増加した。詳細ページの実データでの速度比較はできず、下記の制御されたテストで検証した。

## 実装

- ダッシュボード: 独立した6件のDBクエリを並列化。DB待ちが6段から1段へ。
- Proxy: Supabase公式のgetClaimsで署名・期限を検証。非対称署名鍵のキャッシュ利用時は認証サーバーへの毎回の往復を省略。対称鍵ではSDKがサーバー検証へフォールバックする。マイページ・更新系のgetUser検証は維持。
- サイドバー: 表示名をonAuthStateChangeから反映し、表示用getUser通信を削除。セッションの表示情報は認可には使用しない。サーバーのSupabase clientはReact.cacheでリクエスト内のみ共有。
- 一覧4画面: DB側で検索・フィルター・並び替え・ページ分割。取得列を限定し、レビュー・日記・英語学習の一覧本文は240文字のプレビューとしてブラウザへ渡す。詳細の本文は維持。
- 一覧操作: URLへ条件を保存、検索は300msデバウンス、入力フォーカス維持、ページ番号表示を最大5個に制限。範囲外ページのPostgREST 416/PGRST103は件数を再取得して補正。
- ワード: 一覧は15件取得。テスト開始時だけ検索・フィルターに一致する全件を500件ずつ取得。全件出題・次セット・誤答再挑戦を維持。削除後は全再読み込みではなくrouter.refresh。
- マイページ: 10回のDBリクエストを集計RPC1回へ。ジャンルの全行取得と日記の重複カウントを除去。SECURITY INVOKER、auth.uidによる本人条件、既存RLSを維持。anon/PUBLICに実行権限を与えずauthenticatedのみ許可。
- 詳細・編集6画面: 本文と関連ワードを並列取得。未存在は404、DB障害はエラー画面へ。
- DB: ユーザー・作成日時・idの複合インデックス4件、関連ワード用部分インデックス3件を追加。追加時の全体件数はレビュー4、日記4、英語学習1、ワード23件で、現時点でのDB走査短縮効果は小さい。
- 既存の未コミットのデモアカウント変更制限を保持。

## 補足・運用

- 初回調査のCOMING_UP/publicテーブル0件は、再調査でACTIVE_HEALTHY/5テーブルに復帰。恒常的な欠落ではない。停止・起動状態の一時的影響を今回のコード変更だけで解消したとは主張しない。
- Supabase Advisorは既存のRLS auth.uid評価に関する警告と、追加直後インデックスの未使用情報を報告。既存RLSポリシーの変更は実施していない。参考: https://supabase.com/docs/guides/database/database-linter?lint=0003_auth_rls_initplan
- Security Advisorの既存警告は漏洩パスワード保護の未設定。今回のDB追加で新しい指摘はなし。参考: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
- SDKへの不正なUTF-8 Cookie入力では500応答も観測した。署名偽造JWTは307で拒否された。不正エンコードCookieに対するエラー応答の整備は今回の性能改善には含めていない。
- getClaimsは署名と期限を検証する方式。ログアウト済みトークン等の即時失効チェックが必要な操作はgetUser等によるサーバー確認を維持する。公式: https://supabase.com/docs/guides/auth/server-side/creating-a-client
- 別環境にアプリを反映する際はsupabase/migrationsの2件を先に適用する。現在接続先には適用済み。アプリは未デプロイ。
